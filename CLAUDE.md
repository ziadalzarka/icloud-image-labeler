# Project Instructions

## Git

- Do not include "Co-Authored-By" lines in commit messages.

## Project Overview

macOS CLI tool that auto-labels iCloud Photos using a local LLM (LM Studio). Queries the Photos library for unprocessed media, sends to LLM for keyword/title/description/OCR generation, and writes metadata back via PhotoScript.

## Architecture

- `labeler/` — main package, run with `python -m labeler`
  - `cli.py` — argparse CLI with `run`, `daemon`, `config`, `migrate` subcommands
  - `config.py` — `~/.image-labeler/config.json` management
  - `daemon.py` — launchd Launch Agent lifecycle, `daemon pause`/`resume`, `daemon status`
  - `report.py` — builds the `daemon status` report: what's in flight and batch progress come from the tail of `daemon.log` (metrics only hold finished items), speed, averages, curve, models and errors from `metrics.db`, and the library split from `library.json`
  - `library.py` — `discover()` saves `~/.image-labeler/library.json` each cycle: photos and videos per `m:` tag, unlabeled, and videos on other frame settings (loading Photos takes minutes, so `daemon status` reads this file and never loads the library itself)
  - `pause.py` — the `~/.image-labeler/paused` file, waiting while it exists, and the thread that stops the labeler after an hour paused
  - `discovery.py` — osxphotos query for unprocessed media
  - `exporter.py` — PhotoKit requests for smaller photo and video versions (`PhotoKitPrefetch` starts them ahead of time), Photos export fallback with HEIC-to-JPEG conversion, video frame extraction (ffmpeg, `FRAME_WORKERS` at a time)
  - `llm.py` — OpenAI-compatible LLM client, response parsing, retry
  - `processor.py` — batch orchestration: photos then videos, each exported on the main thread, labeled in worker threads, then written; error tracking
  - `transcriber.py` — optional Whisper transcription of videos, with mlx-whisper on the Mac or a Whisper server (`whisper_url`), called from video processing
  - `migrate.py` — `migrate normalize-keywords` and `migrate redo-transcripts` commands for existing libraries
  - `writer.py` — metadata writes: keywords and title through PhotoKit, the description through Photos.app's AppleScript
- `devbox/whisper/` — the faster-whisper server (Docker, CUDA) that runs on devbox. Huddle's live transcription uses the same server, so devbox loads Whisper once: `/transcribe` also takes `prompt`, `beam_size` and `temperature`, `priority=live` puts a request ahead of any waiting ones (not the one running), and `POST /load` loads the model without audio

## Key Constraints

- Photos are requested through PhotoKit at `max_dimension` (`_image_request`) and videos as Photos' 720p version (`_video_request`), both on the main thread, so iCloud-only items don't download the original (a 4K video is 360-700 MB, iCloud gives about 4.7 MB/s). Requests for the next `PHOTO_PREFETCH` photos or `VIDEO_PREFETCH` videos are started before the current one is used, so downloads run at the same time (cold photos: 1.8 s each one at a time, 0.22 s with 32 started ahead). The item exported next is the first of those whose request has finished (`PhotoKitPrefetch.next_ready`), so one slow iCloud download doesn't hold up the rest; each item waits at most `PHOTO_EXPORT_TIMEOUT` or `VIDEO_EXPORT_TIMEOUT`, counted from when it first reached the front. A video that is only in iCloud and whose 720p version doesn't arrive in that time fails at once and is tried again next cycle: before 0.9.2 it then waited for the Photos export of the original and a Photos restart, about 15 minutes for each such video, while every other video waited. When PhotoKit access isn't allowed or returns nothing (e.g. slow-motion videos give an `AVComposition`), the Photos export of the original is used
- A video is skipped for good as having no usable source only when Photos' 720p version or the original on the Mac was there and ffprobe found no video stream in it. When neither was there, `_resolve_video_path` raises `VideoNotDownloaded` and the video is tried again next cycle. Photos' export of an iCloud-only video whose original it hasn't downloaded is a 691-999 byte file with no video stream, and until 0.10.2 that, or an export that returned nothing, was recorded as "No usable video source", which `PERMANENT_FAILURE_PATTERNS` skips forever. 130 videos (May to Nov 2026, 127 iCloud-only at the time, 75 of them labeled or transcribed fine earlier) were skipped that way until their rows were deleted on 26 Nov 2026
- Every PhotoKit export and write runs inside `objc.autorelease_pool()`. Without it each exported photo kept its `PHAsset`, `CGImage` and `IOSurface` (about 3.6 MB): the daemon reached 19 GB after 5,000 photos and the Mac swapped until exports, writes and LLM calls were all several times slower. A video's `AVAsset` is held until `exported_video` exits, since its file is read after the request returns
- `use_photos_export=True` always for that export (not just for missing/iCloud-only files)
- Keywords and title are written with PhotoKit's private `PHAssetChangeRequest` setters `setKeywordTitles:` and `setTitle:` (about 16 ms, no Photos.app). `setAssetDescription:` is refused without an Apple entitlement (`isClientEntitled` is false), so the description is set with one AppleScript command, written before the keywords so an item never carries its new `m:` tag with an old description. Existing keywords are read with `PHKeyword.fetchKeywordsForAsset_options_`. If PhotoKit access isn't allowed or a change fails, everything is written through AppleScript (`_write_with_applescript`)
- PhotoKit keyword and title changes are saved by one thread (`_PhotoKitSaver` in `writer.py`) that puts everything waiting into one `performChangesAndWait` call, up to `PHOTOKIT_BATCH_SIZE`. photolibraryd saves one change at a time, and a save that adds or removes a keyword loads every photo that has that keyword (the `m:` tags are on tens of thousands), so one save per photo took about 1 s even when idle and 4-6 s each with 64 at once, while 10 photos in one save took 0.45 s. If a grouped save fails, each photo in it is saved on its own, and a photo whose change still fails is written through AppleScript
- Every AppleScript `set` makes Photos.app run a modal loop on its main thread until the library save finishes, so Photos.app handles one save at a time and each costs about 1 s while the labeler is busy. photoscript's setters also read the value back and set it again up to 5 times when it differs, and Photos returns keywords sorted, so every photoscript keyword write ran 5 times (7 saves per photo). The writer uses its own compiled AppleScript (`_PHOTOS_SCRIPT_SOURCE`) instead of photoscript's setters
- AppleScript writes must be serialized (AppleScript is single-threaded) — `_write_lock` in `writer.py`. PhotoKit writes don't take the lock. The description command takes about 0.06 s
- Photos.app can hang with no window, answering every script command only when it times out after 120 s. An AppleScript write that fails after `PHOTOS_HUNG_AFTER_S` force-quits Photos, opens it with `open -a`, waits `PHOTOS_RESTART_WAIT_S` and tries once more (`_update_photo` in `writer.py`). photoscript's own retry is off (`configure_run_script(retry_enabled=False)`): it quits Photos and starts it again with a script command, which is how the hung Photos of 22 Nov 2026 was started
- The writer's AppleScript is compiled with `osacompile` in a subprocess with a `PHOTOS_HUNG_AFTER_S` timeout, and the compiled script is loaded from the file (`_compiled_script` in `writer.py`). Compiling asks a running Photos for its scripting terms with no timeout; on 23 Nov 2026 Photos was still starting and never answered, so the first write held `_write_lock` and every worker waited forever. A compile that times out counts as Photos not responding
- `daemon pause` makes `~/.image-labeler/paused`. While it exists no export starts and every Photos write waits (`_photos_write` in `writer.py`, which checks before and after taking `_write_lock`). A write still waiting when the labeler stops raises `StoppedWhilePausedError` and writes nothing. `daemon pause --minutes N` (1 to `MAX_PAUSE_MINUTES`, 60) writes the time to carry on into the file; once that time passes the pause counts as over (`Pause.is_over`), and nothing stops. Without `--minutes` the file is empty, and after `PAUSE_LIMIT_S` (1 hour, counted from the file's mtime) the daemon unlinks its plist and runs `launchctl remove`, so launchd sends SIGTERM and doesn't restart it; a `run` in a terminal just stops. The daemon is told apart by `XPC_SERVICE_NAME`. `daemon start` clears the pause, and a new run clears one that is over or has expired (`clear_if_over`)
- Exports run one at a time on the main thread (osxphotos SQLite is bound to it); LLM requests run in up to `threads` worker threads. An item gives its LLM slot back before it writes (`_label_with_retry` returns the write step), and there are `WORKERS_PER_LLM_SLOT` times `threads` worker threads, so items waiting to write don't hold up labeling, and the items waiting at once end up in the same PhotoKit save. Photos and videos are separate phases in `processor.py` (`_label_in_parallel`). A 429 from the LLM server is retried with backoff
- Video frames are labeled `video_frame_batch` at a time, then a text-only request merges the batch labels (`label_video` in `llm.py`)
- Videos get a `v:<hash>` keyword of `video_frames`/`video_frame_batch` next to the `m:` model tag. Normal runs relabel labeled items whose `m:` tag is of a model no server in the pool uses or that have no `m:` tag at all (labeled before the tag was added in April 2026, about 62,000 photos), and videos without the current `v:` tag, newest first, up to `OUTDATED_PHOTOS_PER_CYCLE` photos and `OUTDATED_VIDEOS_PER_CYCLE` videos per cycle (loop mode skips the sleep while more remain); `--reindex` takes all of them
- The `reasoning_effort` config (per server or global) is sent with every request when set. When it's empty, photo and frame requests send none and the video merge request sends `reasoning_effort="none"` (thinking made it take 110-300s on a local Qwen); servers that reject the parameter get the request again without it
- A reply that stops with `finish_reason="content_filter"` is asked for again with `ocr_text` empty and no quoted text (`_request_labels` in `llm.py`). OpenAI's filter cuts the reply off partway when the model copies song lyrics or a book page word for word, so the JSON never parses and the item failed on every cycle. Every row where the filter cut a reply off has `content_filtered=1` in `item_metrics`. If the second reply is cut off too, `ContentFilteredError` is recorded as an error and discovery skips the item from then on (`get_permanent_failure_uuids`), so a fallback model can find these with `status='error' AND content_filtered=1`
- Each `metrics.db` connection waits up to `BUSY_TIMEOUT_S` (60 s) for the write lock, and `record_item` logs a warning instead of raising when the row still can't be saved. By then the item is already written to Photos: one grouped PhotoKit save finishes up to `PHOTOKIT_BATCH_SIZE` items at once, and on 25 Nov 2026 17 of 71 photos in one save were marked failed after SQLite's default 5 s wait, although their labels were written
- Qwen models return `<think>` blocks — stripped before JSON parsing in `llm.py`
- Images resized to `max_dimension` before sending to LLM to avoid context window exhaustion
- All keywords are written lowercase, without commas, and deduplicated (`normalize_keywords` in `writer.py`). Photos' Info window splits keywords at commas when the keyword field is clicked
- Under Homebrew the daemon plist uses `/opt/homebrew/opt/icloud-image-labeler/...`, not the versioned Cellar path that `brew upgrade` deletes (`_homebrew_opt_path` in `daemon.py`)
- Transcription is optional (`transcribe` config, `mlx-whisper` is an optional extra, or `whisper_url` points at the devbox server, which takes 16 kHz int16 PCM on `POST /languages` and `POST /transcribe` and returns Whisper's raw scores so the filtering stays on the Mac) and part of video labeling: the video is exported once, transcribed, and the transcript goes into the merge request (`label_video`), so labels use what is said. A video with a `trans:` keyword reuses it instead of running Whisper again. Every video gets one of `trans:<text>`, `trans:no-speech` or `trans:no-audio`
- Labeled videos (`m:` tag) without a `trans:` keyword are found by `get_untranscribed_videos`, up to `UNTRANSCRIBED_VIDEOS_PER_CYCLE` per cycle, and handled after the cycle's other videos: transcribe, then a text-only request (`add_transcript_to_labels`) updates title, description and keywords. Their `m:`/`v:`/`ocr:` keywords are kept (`write_labels_with_transcript`). These rows are recorded in metrics with `media_type='transcript'`
- Labeling keeps `trans:` keywords when it rewrites keywords, and a video whose only keywords are `trans:` ones still counts as unlabeled (`is_unlabeled` in `discovery.py`)
- Whisper invents text on music, noise and silence ("thank you for watching", "اشتركوا في القناة", text in a language nobody spoke). With `whisper_languages` set, the language is detected per 30 s window; windows where the listed languages together score below 0.5 are skipped and each other window is transcribed in its own language (`_window_languages` in `transcriber.py`). Segments are dropped by `_is_speech`: avg_logprob below -1.0, compression_ratio above 2.4, no_speech_prob above 0.85 (or above 0.6 with avg_logprob below -0.5), or only phrases from `MADE_UP_PHRASES`. These thresholds were picked on 75 videos from the library; song lyrics score 0.6-0.8 no_speech_prob and are kept
- `migrate redo-transcripts` removes `trans:` keywords (keeping `trans:no-audio`) so videos are transcribed again with the current settings
- Audio is taken from the first audio track (`-map 0:a:0`); newer iPhone videos also carry an `apple_apac` spatial audio track that older ffmpeg builds can't decode
